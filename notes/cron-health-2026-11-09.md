# 크론이 죽는 걸 보는 인프라 — 무엇을 찾았고, 무엇이 사람 손으로 남는가

**2026-11-09.** 원석님 지시: *"모든걸 감시 감독 검수 qa 하는 인프라를만들어 크론 꺼지는거
보는거까지."*

바로 GitHub Actions의 실제 실행 기록을 전수로 당겨봤다(추측 아님, `gh api .../runs` 직접 호출).
**30분도 안 걸려서 지금 살아 있는, 아무도 모르는 실패를 하나 찾았다.**

---

## 1. 지금 당장 — 11/8 주간 캐러셀이 조용히 실패해 있었다

```
가장 최근 weekly-carousel.yml 스케줄 실행 (2026-11-08 08:48 UTC = 11-08 17:48 KST)
  ✓ 슬라이드 3장 생성   ✓ GitHub Release에 호스팅   ✗ Publish carousel to Instagram
  → urllib.error.HTTPError: HTTP Error 400: Bad Request   (본문 없음)
```

슬라이드는 만들어졌는데 **발행만 400으로 죽었다.** 아무 데도 알림이 안 갔다 — 캐러셀을
감시하는 코드가 이 저장소에 전혀 없었다. 왜 400인지는 로그에 안 남아 있었다:
`post_instagram._post()`가 `_get()`과 달리 **HTTPError의 응답 본문을 한 번도 풀어본 적이
없었다** — Meta가 실제 이유를 담아 보낸 본문을 그대로 버렸다(RULES.md H0, 2026-10-07에
`_get`만 고쳐졌고 `_post`는 그 뒤로 한 달 넘게 같은 구멍으로 남아 있었다).

**고쳤다** — `_open()` 하나로 합쳐서 `_get`·`_post` 둘 다 같은 길을 쓴다. `check_rules.py`도
"문자열이 파일 어딘가 있다"가 아니라 "`_get`과 `_post` 둘 다 실제로 `_open`을 거치고 raw
`urlopen`을 안 쓴다"를 소스 레벨로 검사하게 바꿨다 — 전에는 `_get`만 고쳐진 상태로도
통과하는 검사였다.

**지난주 캐러셀을 다시 올릴지는 콘텐츠 판단이라 손대지 않았다** — 요일이 지났고 중복/타이밍
규칙(RULES.md C)이 걸릴 수 있어 원석님 확인이 필요하다.

## 2. 새로 만든 것 — `cron_health.py`

다른 모든 감시(`watch.py`)는 **결과**를 본다(게시가 됐는지, 좋아요가 괜찮은지). 이건
**그 결과를 만드는 인프라 자체**가 살아 있는지를 본다 — GitHub의 실행 기록에 직접 물어서.

```
watch.py (하루 6회) → cron_health.findings() → 아래 표의 워크플로 전부를 GitHub API로 확인
```

| 워크플로 | 설정상 주기 | 실측(2026-11-09, 86~126일치 전수) | 알림 한계 |
|---|---|---|---|
| comment-reply.yml | 10분 | **중앙값 48분, 최악 12.3시간** (1000건) | 24시간 |
| insights.yml | 매일 | 최악 30.1시간 (96건) | 36시간 |
| refresh-token.yml | 매주 | 최악 171시간≈7.1일 (12건) | 9일 |
| weekly-carousel.yml | 매주 | 최악 177.6시간≈7.4일 (19건) | 9일 |
| reference-study.yml | 2주(자체 페이싱) | 아직 한 번도 안 돎(정상 — 첫 발화일 11-15) | 24일 |

**한계값은 cron 식이 아니라 실측에서 나왔다.** "10분마다"라고 설정했다고 10분마다 도는 게
아니다 — GitHub은 분당 미만 간격의 크론을 심하게 지연시킨다(문서화된 동작). 설정값을
그대로 한계로 썼으면 매일 오탐이 났을 것이다.

**추가로, 마지막 스케줄 실행이 성공(success)이 아니면 즉시 알린다** — 1000+96+12건의
과거 성공률이 사실상 100%였기 때문에(캐러셀의 이번 1건이 유일한 실패), 연속 실패를
기다릴 필요 없이 단 1건의 실패도 믿을 만한 신호다. 이게 §1의 캐러셀 실패를 잡는 경로다.

## 3. 못 고친 것 — GitHub 전체가 죽으면 아무도 모른다

`cron_health.py`도 `watch.yml`이라는 **스케줄 워크플로 안에서** 돈다. 만약 GitHub Actions가
이 저장소의 **모든** 스케줄을 한꺼번에 멈추면(전체 장애, 과금 중단, 저장소 설정 변경 등)
`watch.yml` 자신도 같이 멈추고, 멈춘 것을 보고할 것도 같이 멈춘다. **저장소 안의 코드로는
이 경우를 원천적으로 못 잡는다** — 감시 대상과 감시자가 같은 플랫폼에 있기 때문이다.

### 사람이 한 번만 하면 되는 일 (선택, 무료)

외부 "데드맨 스위치" 서비스 하나가 필요하다 — GitHub과 무관한 곳에서, "이 핑이 일정 시간
안 오면 나에게 알려라"를 해주는 서비스. 가장 간단한 선택: **healthchecks.io** (무료 플랜
충분, 가입만 하면 됨).

```
1. healthchecks.io 가입 → 새 체크 생성
   Period: 4 hours   Grace: 2 hours
   (watch.yml이 하루 6회, ~4시간 간격으로 돌기 때문)

2. 발급된 핑 URL을 시크릿으로 등록
   gh secret set HEALTHCHECK_URL
   → 붙여넣기 (https://hc-ping.com/<uuid> 형태)

3. 끝. watch.yml이 매 실행 끝에 자동으로 그 주소를 한 번 호출한다.
   설정 안 해도 아무것도 깨지지 않는다 — 시크릿이 없으면 그 단계가 조용히 스킵된다.
```

설정하면: GitHub이 이 저장소의 스케줄을 전부 멈춰도, healthchecks.io가 6시간 안에 핑을
못 받으면 **이메일로** 원석님께 직접 알린다 — Telegram도 Actions도 아닌, 완전히 다른 경로로.

**아직 설정 안 됨.** 나머지 코드는 다 됐고 이 한 걸음만 남았다 — IG 인사이트 토큰과 같은
모양(코드는 끝, 가입 1회만 사람이).
