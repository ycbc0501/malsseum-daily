## 1. 붕괴 폭이 부풀려져 있었다 — 그리고 미약한 반등이 이미 있다

**먼저 정정한다.** 이 문서를 쓰기 시작할 때 읽은 숫자는 틀린 숫자였다. §2b 의 버그 때문에
최근 게시물은 **게시 다음 날 숫자에서 얼어붙어** 있었고, 붕괴 전 게시물은 한참 뒤에
백필되어 충분히 익은 숫자였다. **최근을 낮게, 과거를 높게 읽는 편향**이다.

오늘 원장을 풀어주자 48건이 갱신됐다. 몇 개만:

```
09-08 전도서 4:6        1 → 10
09-11 이사야 14:7       2 →  8
09-12 요한복음 6:20     2 →  9
09-01 마태복음 11:28    2 →  9
```

주 단위 평균(좋아요+댓글), **정정 후**:

```
W32  n=15  14.2
W33  n=15  17.2
W34  n=15  22.3     ← 붕괴 직전 주
W35  n=13  12.8     ← 08-27 절벽
W36  n=14   7.2     ← 바닥
W37  n=12   9.2     ← +28%
W38  n= 1   6.0     (오늘 게시 1건, 아직 안 익음)
```

두 가지가 달라진다:

1. **절벽은 여전히 실재한다** — 22.3 → 12.8 → 7.2. 붕괴 자체는 정정 후에도 남는다.
   다만 "15 → 1" 이 아니라 **"22 → 7"** 이다. 1/15 이 아니라 1/3.
2. **W36 → W37 에서 처음으로 올라왔다** (7.2 → 9.2, +28%). 그리고 이 비교는
   회복에 **불리한** 쪽으로 편향돼 있다 — W37 게시물이 W36 보다 **덜 익었는데도** 더 높다.
   둘 다 오늘 같이 갱신됐으므로 측정 시점은 동일하다.

> 판정: **"반등이 전혀 없다"는 내 첫 판단은 틀렸다.** 미약하지만 방향은 위다.
> 그렇다고 기다림이 정답이라는 뜻은 아니다 — 3주 만에 22 의 40% 지점이고,
> 이 속도면 원래 수준 복귀까지 한참이다. 아래 수단은 그대로 유효하다.

팔로워는 08-06 186명 → 09-14 198명 (+12). 죽지는 않았고, 늘지도 않는다.

### 2c. views 의 진짜 차단 사유가 로그에 찍혔다

```
insights tier reach..(9) rejected: HTTP 400:
  (#10) Application does not have permission for this action (code=10)
```

토큰이 아니라 **앱에 권한이 없다.** `IG_ACCESS_TOKEN`(페이스북 로그인 시스템 유저 토큰)은
`instagram_manage_insights` 를 못 받는다 — 비즈니스 관리자에서 SMS 2FA 를 통과해야 하는데
그 번호로 메타 코드가 안 온다. 그래서 `ig_login.py` 가 존재한다: **인스타그램 로그인**으로
읽기 전용 토큰을 따로 발급받는 우회로다.

**`IG_INSIGHTS_TOKEN` 시크릿은 아직 비어 있다. 그것이 채워지기 전에는 조회수를 영영
기록할 수 없다.** 코드는 전부 준비됐고, 남은 건 발급 한 번이다:

```
export IG_APP_ID=... IG_APP_SECRET=...     # Meta 앱 → Instagram → API setup
python3 ig_login.py --auth-url             # 뜬 URL 로 로그인·승인
python3 ig_login.py --code 'AQB...'        # 리다이렉트의 code= 붙여넣기 → 60일 토큰
# 나온 토큰을 저장소 시크릿 IG_INSIGHTS_TOKEN 에 넣는다
```

## 2f. 플래그된 10건을 실제로 열어보니 — **전부 이번 주 새 게시물이었다**

**이것이 모든 것을 바꾼다.**

1. **중복 구절 이론으로는 설명되지 않는다.** 이 셋은 각각 **한 번씩만** 나간 구절이다.

2. **09-08 의 아카이브는 실패한 게 아니라 다시 채워진 것이다.** 10건을 치웠는데 다시 10건이다.
   **새 게시물이 올라가는 족족 플래그되고 있다.** 아카이브는 러닝머신이다.
3. **소재 재사용이 아니다.** 오늘 게시물의 빌드 로그:
   ```
   veo motion attempt 1/2/3 … reel(veo native, 2 segment(s)): 신명기 1:29
   ```
   이미지는 Higgsfield 생성, 모션은 Veo 생성, 음악은 Lyria 생성. **100% 우리가 만든 것이고
   8시간 전에 세상에 처음 나왔다.** 픽셀 한 장도 재사용하지 않았다.

## 2l. 플래그된 게시물 실물 — 조회수 첫 관측값 (09-14 12:01)

신명기 1:29 릴([DdPZFqVk5HQ](https://www.instagram.com/reel/DdPZFqVk5HQ/)), 게시 후 약 7시간:

```
조회 59 · 좋아요 8 · 댓글 1        (원장은 좋아요 5 — 야간 갱신 전이라 3 뒤처져 있음)
오디오: "saintseoul_studio · 오리지널 오디오"
```

세 가지가 읽힌다:

1. **콘텐츠가 문제가 아니다.** 반응률 9/59 = **15%**. 이건 낮은 수치가 아니라 **높은** 수치다.
   본 사람은 반응한다. **본 사람이 없을 뿐이다.**
2. **조회 59 / 팔로워 198 = 30%.** 비팔로워 도달이 0인 정도가 아니라, **팔로워에게도 절반
   넘게 안 닿고 있다.** 제재가 추천만 끄는 게 아니라 피드 노출까지 누르고 있다는 뜻이다.
3. **오디오는 용의선상에서 빠진다.** 인스타그램이 이 릴의 오디오를 **"saintseoul_studio ·
   오리지널 오디오"** 로 귀속시키고 있다. Lyria 생성 음원을 우리 것으로 인정한다는 뜻이다.
   §2k 의 두 범주 중 남는 것은 **텍스트와 형식**이다.

### 그래서 손으로라도 재기로 했다

`IG_INSIGHTS_TOKEN` 이 생기기 전까지 조회수는 API 로 못 받는다. 그런데 조회수는 앱에
**보인다.** 좋아요는 분포의 후행·잡음 지표이고, 우리가 쫓는 사건은 **분포 사건**이다.

```
python3 metrics.py views "신명기 1:29" 59
```

`views_manual: true` 로 표시해서 API 값과 구분하고, 나중에 진짜 값이 들어오면 마커까지
같이 지운다. **첫 관측값 59 를 원장에 넣었다.**

> 하루 두 번, 앱에서 조회수만 읽어 이 명령을 돌려두면 캡션 실험(§2j)의 효과를 **좋아요가
> 아니라 도달로** 판정할 수 있다. 토큰이 생기면 자동으로 대체된다.

### 확인할 것 하나 — Meta Verified 라면 사람에게 문의할 수 있다

스크린샷의 계정명 옆에 **파란 배지**가 있다. 이것이 **Meta Verified(유료 구독)** 이라면
**계정 지원(고객 문의)** 채널이 열려 있다. 오탐으로 걸린 추천 제한은 검토 요청보다
**사람에게 설명하는 쪽이 빠른 경우가 많다.** 확인 필요:
설정 → **Meta Verified** 항목이 있는지 → 있으면 **지원 문의**로 이 건을 올릴 것.

### D. 유입구가 추천 하나뿐이다 — 이게 구조적 문제

현재 이 계정이 새 사람에게 닿는 경로:

| 경로 | 상태 |
|---|---|
| 릴스 추천 | **제재로 막힘** |
| 해시태그 | 스스로 포기 (`hashtags.py`: "해시태그는 도달을 만들지 않는다" — 5개 고정) |
| 트렌딩 오디오 | 없음 (Lyria 자체 생성 음원 → 오디오 페이지 유입 0) |
| 협업·리믹스·스레드 | 없음 |

**즉 추천이 막히면 유입이 0이 된다.** 제재가 풀리기를 기다리는 것 말고 방법이 없는
구조를 우리가 직접 만들었다. 추천 바깥의 유입구를 **하나라도** 만들어야 한다:

- **스레드(Threads) 교차 게시** — 메타 계열이라 프로필 방문으로 직결되고, 텍스트 말씀은
  스레드 포맷에 그대로 맞는다. 자동화 비용도 가장 낮다.
- 트렌딩 오디오를 쓰는 실험 — 다만 RULES 의 음악 규칙과 충돌하므로 규칙 개정이 먼저다.

### E. 콘텐츠에서 숫자가 말해주는 것 (붕괴 전 132건 기준)

| | |
|---|---|
| 테마 최고 | 감사 20.1 · 평안 18.4 · 은혜 18.3 |
| 테마 최저 | **위로 8.2** (n=13) — 다른 테마의 절반 |
| 포맷 | REELS 17.2 > FEED 9.2 |

- 붕괴 *후* 에는 FEED 7.7(n=3) > REELS 4.3(n=31) 로 뒤집힌다. n=3 이라 결론은 못 내지만,

평상시 수준이었다. 플래그를 안 받았다면 추천에서 빠지지 않았다는 뜻이고, 숫자가 맞는다.

### 8c  필요한 확인 — 스크롤 한 번 (이것이 다음 한 수)

목록을 **끝까지 내려서**:

1. **전체 몇 건인가** (09-14 에는 10건이었다)
2. **피드/캐러셀 게시물이 한 건이라도 있는가** — 09-13 시편 4:8, 그 이전 주 캐러셀들

```
python3 metrics.py flagged    "<목록에 있던 ref>" …
python3 metrics.py notflagged "시편 4:8"
python3 metrics.py flagreport 2026-09-10
```

### 8d  확인되면 무엇을 하나

**피드가 정말 안 걸린다면** 형식 축이 원인이고, 가장 싼 조치는 **저녁 슬롯을 며칠간
캐러셀로 돌리는 것**이다 — 릴 파이프라인을 건드리지 않고, 판정은 다음날 아침 목록에서 난다.
다만 이는 포맷 비중 변경이라 **계정 주인 결정**이며, 오늘은 **아무것도 바꾸지 않았다**
(5/5 연속 성공 중인 파이프라인을 증거 n=1 로 흔들지 않는다).

**피드도 걸린다면** 형식은 무관하고 남는 건 **개역개정 본문 그 자체**다. 그 경우 렌더
변주는 전부 헛수고이며, 우리 문장이 주가 되고 말씀이 인용이 되는 구성 — 즉 브랜드 자체의
변경 — 이 유일한 길이 된다.

### 8e  곁가지 — 원장 포맷이 매번 뒤집히고 있었다

오늘 푸시가 **metrics.json 전체(2,387줄) 충돌**로 막혔다. 원인은 내용이 아니라 모양이다:
`metrics.save()` 는 `indent=1, sort_keys` 로, `ledger_merge.py` 는 compact 한 줄로 쓴다.
CI 가 원장을 저장할 때마다 포맷이 뒤집히고, 그 다음 커밋은 **한 항목만 바뀌어도 전체 파일
diff** 가 된다. 동시 푸시가 나면 한 항목이 아니라 파일 전체가 충돌한다 —
`ledger_merge.py` 가 막으려고 만들어진 바로 그 상황이다(08-26 원장 분실).

`ledger_merge.py` 가 **파일의 원래 작성자와 같은 모양으로** 쓰도록 고쳤다
(metrics.json → indent=1/sorted, state.json → compact 유지). 병합 로직은 그대로다.

`comment_reply.poll()` 은 답글을 보낸 뒤 큐에서 지운다. 그런데 `save_ledger.sh` 는

"우리가 지웠다" 와 "우리에겐 원래 없었다" 를 구분할 수 없으므로 **원격에 남아 있는 키가

매 실행이 답글을 보내고, 지우고, 되살리고, 다음 실행이 또 보낸다.

이 저장소의 다른 원장은 전부 append-only(구절·클립·지표·카운터)라 이 결함이 드러나지 않았다.
**`pending_replies` 하나만 작업 큐**였고, 큐의 본질은 완료 항목의 삭제다.

### 9c  고친 방식 — `replied_publicly` 가 권위다

큐를 믿지 않는다. 보내기 직전 **이미 답글한 id 면 큐에서 버리고 건너뛴다.** 병합이 무엇을
되살리든 두 번 보내지지 않는다. `ledger_merge.py` 문서 맨 위에 **"여기서는 삭제를 표현할 수
없다"** 를 못박았다 — 삭제가 필요한 원장을 새로 만들려는 다음 사람이 먼저 읽도록.

`test_comment_reply.py` 9건 추가, CI 에 연결. **고치기 전 코드로 돌려서 실패하는 것을

## §10  게시 4회 연속 실패 — 지역 import 하나가 함수 전체를 망가뜨렸다 (2026-09-19)

### 10a  증상

```
09-18 19:00  ❌   09-19 05:00  ❌   09-19 19:00  ❌ (+ 재시도 여러 건)
```

알림은 **정확히 작동했다** — 실패 링크 3건, 누락 경고 2건이 이 방으로 왔다.
(감시 장치는 이제 신뢰할 수 있다. 문제를 안 만들 뿐, 있는 문제는 알린다.)

### 10b  원인

```
UnboundLocalError: cannot access local variable 'fetch_higgsfield'
  daily_post.py:461  scene_i, scene_cat = fetch_higgsfield.pick_scene(...)
```

`daily_post.py` 32행에 모듈 수준 `import fetch_higgsfield` 가 있는데, `main()` **549행에
지역 import** 가 하나 더 있었다. 파이썬은 함수 본문 전체에 대해 이름을 지역으로 묶으므로,
**90줄 위의 사용이 UnboundLocalError** 가 된다.

가장 나쁜 형태의 실패였다: 이미지 생성 → 게이트 → Veo → 음악까지 **전부 돌고 나서**
게시 직전에 죽는다. 매 실행이 API 비용을 다 쓰고 아무것도 안 올린다.

### 10c  왜 안 걸렸나

| 검사 | 통과 여부 | 이유 |
|---|---|---|
| `compileall` | ✅ 통과 | 문법은 정상이다 |
| `audit_refs` (교차참조) | ✅ 통과 | `fetch_higgsfield.pick_scene` 은 **실제로 존재한다** |
| `check_rules` | ✅ 통과 | 규칙 위반이 아니다 |
| 테스트 | ✅ 통과 | `main()` 을 실행하는 테스트가 없다 |

**그 줄을 실제로 실행해야만 드러난다.** 4단계 재검수를 두 번 돌리고도 이게 남은 이유다 —
검수는 "있는 것"을 검사했고, 이건 "바인딩 시점"의 문제다.

### 10d  고친 것

- 지역 import 삭제(모듈 수준 것이 이미 있다). 자리에 **왜 넣으면 안 되는지** 주석으로 남김.
- **`audit_refs.shadowed_imports()` 신설** — 모든 함수에서 *지역 import 보다 앞선 사용*을
  찾는다. 고치기 전 커밋에 돌려서 **3건 전부 잡는 것을 확인**했다
  (`daily_post.py main() 461/487/490 ← import at 549`). 지금 저장소는 깨끗하다.
- `verify.sh` 가 `audit_refs.py` 를 이미 부르므로 **매 푸시마다 돈다.**

### 10e  상태 (이 문서를 쓰는 시점)

- 수정 푸시 완료: `4f9a858`, 감사 푸시 완료.
- **강제 게시 실행 중** — run 35436412760. 원격에서 돌고 있으므로 이 세션이 끝나도 계속된다.
  성공하면 오늘 저녁 슬롯이 채워지고, 실패하면 **실패 알림이 이 방으로 온다.**
- **09-18 저녁과 09-19 아침 두 슬롯은 비어 있다.** 지난 슬롯을 소급해 채울지는 판단이 필요하다 —
  하루에 3건을 몰아 올리는 것이 퍼온 콘텐츠 판정 중인 계정에 이로울 리 없다. **채우지 않는 쪽을
  권한다.**

## §11  알림이 거짓말을 하고 있었다 — 실패한 건 실행이지 슬롯이 아니다 (2026-09-19)

### 11a  사실 확인부터

계정 주인이 "저녁 것도 또 실패했네"라고 했다. **틀렸다 — 저녁 게시는 올라갔다.**

```
09-19 19:18 KST  고린도전서 15:55   ✅ (media 17886895230617040, 릴 4세그먼트)
```

수정(`4f9a858`) 이후 실행은 **전부 성공**이다(10:04Z · 11:41Z · 12:10Z · 12:52Z).
화면의 마지막 ❌(7:03 PM)는 **수정 전 마지막 실행**이다.

**그런데 그렇게 읽은 것이 정상이다.** 알림창에 ❌ 가 다섯 개 있고, 그 뒤로 아무 말이 없다.
읽는 사람이 "실패했다"고 결론짓는 것이 합리적이다. **문제는 읽은 사람이 아니라 채널이다.**

### 11b  두 개의 결함

1. **알림이 슬롯을 모른다.** `daily-post.yml` 이 실패한 **실행마다** `notify.py` 를 직접 불렀다.
   체인은 원래 재시도하고 물러선다 — 슬롯이 이미 채워진 뒤 실패한 실행도 ❌ 를 보낸다.
   09-19 에 다섯 개가 그렇게 나갔다.
2. **아무도 루프를 닫지 않는다.** 슬롯이 나중에 채워져도 **마지막 말은 영원히 ❌** 다.

두 번째가 더 나쁘다. **마지막 말이 항상 ❌ 인 채널은 신뢰를 잃고, 신뢰를 잃은 알림은 없는
알림이다.** 알람봇을 이 방으로 옮긴 이유(G-1)가 정확히 "안 읽히는 알림"이었는데, 같은 실패를
다른 방식으로 반복하고 있었다.

### 11c  고친 방식

`watch.py --post-failed <run-url>` 로 바꿨다(워크플로는 이제 `notify.py` 를 직접 안 부른다):

- **인스타그램에 슬롯이 비었는지 먼저 묻는다.** 채워졌으면 **아무 말도 안 한다.**
- **한 슬롯당 최대 한 번.** `watch.json` 에 `failed-<날짜>-<시>` 로 기록.
- 그 슬롯이 나중에 채워지면 **`✅ 해결됐습니다`** 를 보내고 기록을 지운다.
- 에피소드 청소 루프가 `failed-*` 를 먹지 않게 예외 처리(안 그러면 해결 메시지가 영영 안 간다).

`RULES.md` G-1 개정. `test_fail_alert.py` **12건** 추가, CI 연결.

### 11d  실측

- CI 녹색(`d7925d7`) — `audit_env` 가 새 env 블록까지 검사.
- 워크플로 수동 실행: 크래시 없음, **헛소리 없음**. 진짜 비어 있는 두 슬롯
  (09-18 19:00, 09-19 05:00)만 쿨다운 상태로 남아 있고 09-19 19:00 은 목록에 없다 —
  **채워졌다고 올바르게 판단하고 있다.**

### 11e  정직하게 남기는 것

계정 주인의 지적("결과 확인도 안 하냐")은 맞다. 지난 턴에 강제 게시를 띄워놓고
**결과를 확인하지 않은 채 턴을 끝냈다.** 다음 턴에 확인해서 성공을 보고했지만, 그 사이
알림창은 ❌ 뿐이었다. 채널을 고친 것과 별개로, **띄운 작업의 결과를 같은 턴에서 확인하는 것**은
지켜야 한다.
